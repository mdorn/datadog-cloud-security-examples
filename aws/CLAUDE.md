# CLAUDE.md

Guidance for Claude (and humans) working in this repo.

## What this project is

A **deliberately insecure** AWS lab, deployed with Terraform, that produces a realistic
**attack path / toxic combination** in **Datadog Cloud Security**. It is used for
Datadog SE demos. It is built one scenario at a time.

Scenario 01 (current) is this chain:

```
Internet ──► EC2 (public IP, SG 0.0.0.0/0:80, IMDSv1, old Ubuntu AMI)
               └─ Docker: Flask to-do app (EOL base image + vulnerable pip libs)
               └─ Instance role ──► s3:GetObject / s3:ListBucket
                                       └─ S3 bucket with synthetic SSNs (SDS finding)
```

What Datadog should show for it:

| Datadog surface | Finding it comes from |
|---|---|
| Misconfigurations (CSPM) | SG open to the world, IMDSv1 allowed, unencrypted EBS, S3 without access logging or versioning |
| Vulnerabilities (host) | Old Ubuntu 22.04 AMI (2023 build), unattended-upgrades turned off |
| Vulnerabilities (container image) | `python:3.8-buster` (Debian 10 and Python 3.8, both EOL) plus extra apt packages |
| Vulnerabilities (app libraries) | `app/requirements.txt` pins (Flask, Werkzeug, Jinja2, PyYAML, requests, urllib3, gunicorn) |
| Sensitive Data Scanner (cloud storage) | `data/customer_records.txt` in the bucket (US SSN library rule) |
| Attack path / toxic combination | Publicly reachable instance + critical vulns + role that can read sensitive S3 data |

The full list of intentional misconfigurations lives in
[`docs/misconfigurations.md`](docs/misconfigurations.md). Update it whenever you add or
remove one.

## Ground rules (read before changing anything)

1. **The misconfigurations are the product.** Never "fix" an intentional weakness
   (open SG, IMDSv1, old AMI, old base image, pinned vulnerable libs, unencrypted EBS,
   broad role) unless asked. If a linter, tfsec, Checkov, Dependabot or a reviewer
   flags one, that is expected. Each intentional weakness has a `# INTENTIONAL:`
   comment. Keep that convention for new ones.
2. **Vulnerable, not exploitable.** The app must never ship anything that hands out
   real code execution or data to the internet:
   - No Flask/Werkzeug debug mode (the Werkzeug debugger is a remote shell).
   - No endpoints that run commands, `eval`, unpickle, `yaml.load` user input, proxy
     to IMDS or read from S3.
   - Only port 80 is open. No SSH, no key pair. Shell access is SSM Session Manager.
3. **Synthetic data only.** `data/` holds fake records generated by
   `scripts/generate_fake_ssns.py`. Never add real PII, real credentials or customer data.
4. **Sandbox account only.** Deploy only into an isolated AWS sandbox account. Tear down
   with `terraform destroy` when the demo is done. Everything is tagged
   `Project=dd-attack-path-lab` and `Owner=<var.owner>`.
5. **Ask before `terraform apply` or `terraform destroy`.** `fmt`, `validate` and `plan`
   are fine to run any time (see `.claude/settings.json`).
6. **Secrets stay out of git.** `terraform.tfvars`, state files and `.env` are
   gitignored. The Datadog API key is a `sensitive` variable; it lands in EC2 user data
   and in state, which is acceptable for a throwaway sandbox only.

## How the app gets onto the instance

No registry. `ec2.tf` reads every file under `app/`, base64-encodes it into the user
data template, and cloud-init writes it to `/opt/todo-app`, then runs
`docker build` and `docker run -p 80:5000`. Consequences:

- Changing anything in `app/` changes user data, which **replaces the instance**
  (`user_data_replace_on_change = true`). That is intended.
- EC2 user data is capped at 16 KB. If the app grows past that, move delivery to an S3
  prefix or ECR (ECR also adds a registry-scanning demo).
- Boot logs: `/var/log/cloud-init-output.log` on the instance.

## Datadog setup (outside this repo)

The lab only creates the vulnerable resources. The Datadog side is set up once per
sandbox account:

1. AWS integration for the sandbox account with **Cloud Security** (resource collection
   for misconfigurations) enabled.
2. **Agentless Scanning** in the lab's region, with **Sensitive Data Scanner for cloud
   storage** turned on. Use a Remote-Configuration-enabled API key. Agentless covers:
   host vulns, container images on the host, and the S3 bucket. Scans run every 12 h;
   `make scan` triggers an on-demand scan.
3. Optional: set `install_datadog_agent = true` to put the Agent on the instance
   (SBOM for host and container images, CSM Threats runtime). Note: Agentless **skips**
   hosts where the Agent runs with both Cloud Security Vulnerabilities and
   Misconfigurations enabled; S3 SDS always needs Agentless.

The bucket uses SSE-S3 (AES256), not KMS, so the Agentless scanner needs no extra key
grants.

## Conventions

- Terraform: one file per concern, `snake_case` names, every resource gets
  `local.name_prefix` in its name and inherits `default_tags` from the provider.
- Mark each intentional weakness with `# INTENTIONAL: <what> -> <expected Datadog finding>`.
- New scenario = new Terraform files (or a module under `terraform/scenarios/`) plus a
  section in `docs/misconfigurations.md` and an entry in `docs/roadmap.md`.
- Vulnerable versions: pin exact versions, and add the CVE IDs in a comment next to the pin.
  Before adding a pin, check it still installs on the base image (old pins often
  conflict, for example `requests==2.19.1` needs `urllib3<1.24`).
- Keep costs low: `t3.micro` default, one AZ, no NAT gateway.

## Known gotchas

- The 2023 Ubuntu AMIs are **deprecated** by AWS, so the AMI lookup sets
  `include_deprecated = true`. If Canonical deregisters them, change
  `ami_name_pattern` in `terraform.tfvars`.
- `python:3.8-buster` is EOL; its apt sources are repointed to `archive.debian.org`
  in the Dockerfile. If that mirror ever breaks, drop the `apt-get` step; the base image
  alone still carries hundreds of CVEs.
- If your account enforces EBS encryption by default, the "unencrypted EBS" finding will
  not appear. Everything else still works.
- First Datadog findings can take up to 12 h without `make scan`, and attack paths need
  the vulnerability and misconfiguration findings to land first.
